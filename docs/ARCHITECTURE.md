# Архитектура DjShrek-Draiver Cyber Club

## Текущее устройство проекта

Текущая реализация — одно WPF-приложение на .NET 8. Описанная ниже структура отражает фактические сервисы и границы ответственности, а не планируемое разбиение на отдельные проекты.

## Реализованные сервисы

- `DeviceInventoryService` — чтение системной информации и инвентаризация PnP-устройств средствами Windows.
- `DriverCompatibilityMatcher` — точное сопоставление Hardware ID и безопасный отказ при неоднозначном общем Compatible ID.
- `InternetDriverCatalogService` — веб-поиск страниц производителей по Hardware ID, HTTPS и allowlist доменов. Поисковая выдача — только указатель на страницу, не подтверждение драйверного пакета.
- `DriverMaintenanceService` — операции Driver Store через штатные средства Windows, экспорт/восстановление и предварительная проверка INF/CAT.
- `OemCatalogService` — определение производителя ПК и переход к его странице поддержки.
- `HardwareSensorService` — чтение доступных аппаратных датчиков; неподдерживаемые значения отображаются как недоступные.
- `RegistryMaintenanceService` — диагностика записей автозапуска и резервная копия перед исправлением.
- `JunkCleanupService` — поиск и очистка старых временных файлов с ограничениями по возрасту.
- `ThemeManager` — применение набора тем оформления.

## Безопасные границы текущего поиска

1. Инвентаризация получает имя устройства и Hardware ID из Windows.
2. Поиск формирует запрос по Hardware ID и ОС.
3. Результаты принимаются только с HTTPS и доменов из явного allowlist.
4. Ссылка связывается с устройством только при точном совпадении Hardware ID.
5. Пользователь открывает страницу производителя и самостоятельно проверяет точную модель и пакет.

Текущий сервис **не** загружает драйверы из выдачи, не извлекает версии из пакета, не проверяет Hardware ID внутри INF, не доказывает совместимость по ОС/архитектуре и не устанавливает найденный результат. Поэтому UI не должен называть найденную страницу «готовым обновлением».

## Целевой безопасный конвейер обновления

До реализации автоматической установки каждый кандидат должен пройти все этапы:

1. Получение метаданных из официального машинно-читаемого каталога производителя.
2. Проверка модели ПК/системного идентификатора, ОС и архитектуры.
3. Сопоставление Hardware ID с моделями, поддерживаемыми INF.
4. Сравнение версии и даты с установленным драйвером; исключение downgrade.
5. Загрузка по HTTPS с проверкой размера, SHA-256 и подписи издателя.
6. Проверка INF/CAT до установки; отказ при неподписанном или неподходящем пакете.
7. Создание резервной копии и запрос явного подтверждения пользователя.
8. Установка через поддерживаемый механизм Windows с повышением прав.
9. Повторная инвентаризация, отчёт и доступный сценарий восстановления.

## Нефункциональные требования

- Не требовать административных прав для чтения информации, где это возможно.
- Запрашивать UAC только для конкретной привилегированной операции.
- Любые изменения системы выполнять после явного подтверждения.
- Отменять сетевые операции по CancellationToken и ограничивать время ожидания.
- Не запускать произвольные EXE из поисковой выдачи.
- Не скрывать отсутствие датчиков, каталога или доказательств совместимости.
- Любая ошибка должна быть показана пользователю без падения основного интерфейса.

## CI и проверка

Windows CI собирает x64 WPF приложение, выполняет UI smoke test и публикует артефакты. Smoke test покрывает наличие шести экранов, темы, системную инвентаризацию, ряд операций обслуживания и проверки URL/Hardware ID. CI не подтверждает визуальное качество на всех DPI, поведение на каждом OEM-компьютере или совместимость реальных драйверных пакетов; для этого нужны отдельные тесты на Windows 10/11.
